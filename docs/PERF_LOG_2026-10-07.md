## 05. What wakes the bar and the compositor at idle  (2026-10-07 19:51)
- Machine: laptop, `schedutil`, live session idle. `sudo perf trace -s -p PID -- sleep 20` (tracefs is not readable by dev; sudo used for read-only tracing only, same purpose as the approved perf setup), bar pid 768 then compositor pid 730; plus `perf trace -p 730 -- sleep 4` for the raw sequence (06).
- Result, 20 s window:
  - Bar: poll 60 calls, read 128, openat 58, close 78, newfstatat 36, sendmsg 56, recvmsg 56, **timerfd_create 20 and timerfd_settime 20 (one per clock tick: `schedule_clock` makes a new oneshot timerfd every second)**, getdents64 11, pread64 9, statfs 4, readlink 4. Syscall CPU time total about 70 ms/20 s of which `read` 59 ms is dominated by one 27 ms read (max); `poll` is the idle wait. Five independent timers exist in the bar: clock 1 s, stats 2 s, disk 5 s, network 5 s, battery 15 s, none aligned.
  - Compositor: epoll_wait 84, ioctl 588 (29/s), getpid 390 (19/s), recvmsg 112, sendmsg 28, rt_sigaction 56 (SIGBUS handler set and cleared around each Mesa upload), read 28 (DRM flip events). Sequence per bar tick (06): commit from the bar (76-byte request) -> GEM_CREATE_EXT 512 KB + SET_DOMAIN + MMAP_GTT (staging buffer for the shm upload) -> EXECBUFFER2 -> second EXECBUFFER2 (the render pass) -> DRM_MODE_ATOMIC page flip -> frame_done to the bar -> wait for the flip event (16.7 ms later) -> read. About 2.5 ms of compositor CPU per clock tick (15 ticks / 60 s).
- Decision: nothing is wasted in the sense of work with no visible change: every tick changes the seconds. The cost of one tick is Mesa+i915 per-frame overhead (see 07/08), not our code. Candidate cheap cuts in the bar (not yet measured as worth it): reuse one periodic timerfd for the clock instead of a new oneshot per second, and align the 2/5/5/15 s timers to the clock tick so one wakeup serves all (fewer wakeups, same output).
- Raw: perflog/2026-10-07/05-wakeup-syscalls.txt, 06-compositor-trace-4s.txt

## 08. perf record of the compositor under a scrolling full-window terminal  (2026-10-07 20:10)
- Machine: laptop, `schedutil`, nested build P (frame pointers, symbols, LTO, goldmont-plus, non-PGO), `perf record -F 3000 --call-graph fp -p PID -- sleep 20` with foot fullscreen running `yes` in the nested compositor (1280x720 output).
- Result: 6573 samples (20 s x 3000 Hz = 60000 possible; the compositor was on-CPU about 11% of the time). By DSO: **libc 58.2%** (one address, `0xadf1b`, alone 53.3%, plus `0xadd09` 2.7%), kernel 13.6%, Mesa gallium 13.1%, wlroots 4.7%, i915 4.4%, wayland-server 1.7%. Kernel part is mostly the `ioctl -> i915_gem_execbuffer2` path (6.4% inclusive), `sendmsg` 1.9%. Our own code (`fleetwm` DSO): `output_frame` 0.20% self and nothing else visible. Per the 2026-10-06 note this libc address is `rep movsb` (memcpy): the call chain is Mesa's shm upload (the client's pixels copied to the GPU staging buffer), so **the copy is about 53% of the compositor's CPU while scrolling, more than the 'a third' measured before**.
- Speed of light (02): memcpy RAM on this CPU is 11.5 GB/s per thread (read+write traffic), so 1 ms moves about 5.7 MB of data. 1280x720x4 = 3.7 MB per full frame = 0.64 ms per full-frame copy; at 60 fps that is 3.9% of a core, the measured 53% of 9% = 4.8% of a core is in line with copying about one full frame per frame (a scrolling terminal damages everything). So the copy runs at about the memory-copy limit; nothing to gain in the copy loop; it is only avoidable by uploading less (smaller damage) or by not having to copy (dmabuf/GPU-buffer clients, which foot is not).
- Decision: the compositor's own code is not the cost. Real work moves to the client side: foot's CPU time (9.1 s in 14 s) dwarfs the compositor's. No compositor change planned from this profile. Rejected idea logged: "faster copy in the compositor": the copy is inside Mesa and runs at the memory limit.
- Raw: perflog/2026-10-07/10-compositor-scroll-perf.txt
