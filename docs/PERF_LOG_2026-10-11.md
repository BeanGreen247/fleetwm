# Celeron post-cap drag A/B (2026-10-11)

## Chromium taskbar launch follow-up (2026-10-11)

This is a reliability observation, not a renderer benchmark. After three
Crashpad dumps at 20:08 showed SIGSEGV in Chromium's Wayland/XKB path, Chromium
was launched by clicking its configured pinned taskbar button on the live
Fleetwm session. This exercised the normal `chromium.desktop` ->
`/usr/bin/chromium` launch with the default profile and Wayland/Ozone backend.
The browser window appeared and its main process remained alive for at least
2:36; no new `.dmp` appeared. The browser was left open for the owner.

This successful trial does not explain the earlier intermittent crash or
establish a fix. No profile, launcher, backend, or compositor setting was
changed. The test environment was not restarted.

## Setup

- Hardware: Intel Celeron N4020, UHD Graphics 600, Mesa GLES2.
- Runtime: installed Fleetwm `0.4.0-78-g9848674-dirty` in a nested Wayland
  compositor with a 1280x720 `WL-1` output; the live 1920x1080 session remained
  running.
- Each trial copied the user's theme into an isolated `HOME` and changed only
  `glass_effects`. The Settings window was opened in the nested compositor and
  verified through its `SUBSCRIBE_WINDOWS` IPC response (`dev.fleetwm.Settings`,
  title `Fleetwm Settings`) before the workload.
- Workload: eight repetitions of titlebar drags `(645,70) <-> (445,250)` and
  right-edge drag gestures `(1049,300) <-> (1149,300)`, using the existing
  `scripts/pgo-pointer.c` helper. The scripted sequence took 2.748-2.767 s.
- Ordering: three balanced pairs, glass/flat, flat/glass, glass/flat.
- CPU: `perf stat -x, -e task-clock` attached to the nested compositor and its
  bar for seven seconds.
- GPU: 16 samples at 500 ms from `intel_gpu_top -J -s 500`. The nested
  compositor's client `Render/3D.busy` was selected by PID; device-wide busy
  is also shown only as context because the live desktop was active.
- These are utilization samples, not GPU frame-time or input-to-present
  measurements. The output was 1280x720, not the user's complete 1920x1080
  desktop workload. The exact resize-edge hit was not independently verified;
  Settings presence and titlebar drag targeting were verified.

## Interpretation and follow-up

The post-cap workload confirms that the nested compositor can briefly reach
Render/3D busy in the mid-40% range while dragging. Its whole-capture average is
about 14%, and disabling glass reduces that average by only about 0.2-1.2
percentage points in these three pairs. CPU task-clock and the duration of the
scripted sequence do not show a repeatable glass penalty. This does not explain
a sustained ~40% report or justify removing glass, changing ISA flags, or
making an unmeasured renderer rewrite.

The 500 ms hardware sampler cannot determine frame cadence, frame-time
deadlines, damaged pixels per frame, or input-to-present latency. The next
code-level hypothesis worth measuring is whether per-pointer-event calls to
`wlr_scene_node_set_position()` accumulate excess damage between the existing
24 FPS output commits. Instrument update counts and damage area per presented
frame before changing that path; do not lower the cap without measuring the
smoothness and latency cost.

Harness integrity: two preliminary batches were discarded after finding a bad
Wayland/IPC socket alias and, in a later attempt, that the pointer helper could
inherit the host display. Neither batch is represented in these results. The
final six trials explicitly set the isolated `XDG_RUNTIME_DIR` and
`WAYLAND_DISPLAY`, confirmed the Settings window through nested IPC, and
completed with no test processes left running. During the discarded
host-display batch, the helper may have sent virtual-pointer drag gestures to
the live session; it sent no click command, no settings were changed, and the
live compositor was not restarted. The final run left live Fleetwm PID 768 and
bar PID 794 running.

## Nested UI process profile (2026-10-11)

To locate app/UI CPU work separately from the renderer, ran Task Manager and
Settings inside an isolated nested Celeron compositor at 1280x720. Both
`XDG_RUNTIME_DIR` and `WAYLAND_DISPLAY` were set for nested clients; the live
session remained untouched. Ten-second per-process `perf stat` captures found:

| Visible client | Client task-clock | Nested compositor | Nested bar | Client Render/3D |
|---|---:|---:|---:|---:|
| Settings (theme page) | below 1 ms | 216 ms | 203 ms | not separately resolved |
| Task Manager (Processes) | 163 ms | 79 ms | 203 ms | no client record in intel_gpu_top |
| Task Manager (Performance) | 58 ms | 48 ms | 195 ms | no client record in intel_gpu_top |

These are short exploratory captures, not per-frame render latency. The
Processes tab adds a once-per-second `/proc` scan, sort, and row drawing; its
observed client CPU was higher than the Performance tab, while the nested
compositor and bar remained the major sampled processes. The output does not
isolate CPU cost within each Task Manager function, and `intel_gpu_top` did not
report a separate client-engine entry for these wl_shm clients.

A first candidate was caching each `/proc/PID/stat` descriptor's UID instead
of `fstat()`ing the descriptor each refresh. Syscall tracing showed 1,653
`fstat` calls before versus 213 after in ten seconds, but a balanced CPU sample
did not show a repeatable improvement. More importantly, process credentials
can change during a process lifetime, so caching UID for the full descriptor
lifetime could make the User column stale. That candidate was rejected and
the per-refresh `fstat()` was retained to preserve current behavior.

The measured optimization instead removes the duplicate copy of the full
process-row vector (including each process-name string) from the Task Manager
refresh path. `TaskMgr` now sorts and draws the `ProcessTable`'s existing rows
directly; the table still rebuilds rates and rows as before. Three balanced
old/new ten-second captures under the same nested compositor measured
Task Manager task-clock at 150.70, 164.21, and 168.03 ms before versus 142.25,
157.90, and 166.50 ms after. All three paired deltas favored the change
(-8.45, -6.31, and -1.53 ms); mean task-clock fell from 160.98 to 155.55 ms,
about 3.4%. This is a small CPU-work reduction in the visible Processes-tab
idle sample, not a measured input-latency, frame-time, or GPU improvement.
Render/3D remained near the background level during these idle-tab runs.
All 12 focused `ProcStats.*` tests and the full 1,127-test suite pass; the
1024x768 headless compositor/Task Manager smoke test passes 13/13.

The nested test compositor, clients, and temporary runtime were terminated
without restarting the live window manager or rebooting the laptop.

## Integrated-GPU memory baseline and candidates (2026-10-11)

The owner corrected the current target address to `dev@192.168.0.182`. SSH
confirmed hostname `uefi-x86`, Celeron N4020, Intel PCI device `8086:3185`
using `i915`, 3.4 GiB system RAM, and the connected eDP panel's active
1920x1080 mode. This is an integrated GPU with shared system memory, not a
discrete GPU with a separately sized VRAM pool. The i915 sysfs interface on
this machine does not expose the discrete-style `mem_info_vram_*` counters.

This machine is a low-end Intel UMA reference, not the only target class.
Fleetwm is intended to support Intel integrated/discrete, AMD
integrated/discrete, NVIDIA discrete, and other supported GPUs. Consequently,
the i915 and `intel_gpu_top` figures below are specific to this device; do
not extrapolate their counters, memory topology, or conclusions to another
vendor. Any future memory comparison should capture dedicated VRAM when
available and shared/system memory separately, identify the backend/device,
and use backend-neutral implementation changes unless a capability check
proves a hardware-specific path is appropriate.

As an idle snapshot of the live 1920x1080 desktop, `intel_gpu_top -J -m -s
500` returned 12 samples over about six seconds. Its per-client system-memory
accounting for the `fleetwm` compositor was 61.57-62.07 MiB resident
(62.07 MiB median); Render/3D busy was 0.00-1.21% (0.41% median). No other
Fleetwm client appeared as a separate GPU context in those records. This is
driver-reported per-client tracked memory, not a complete inventory of every
system allocation, a dedicated-VRAM figure, or a peak under active use.

Code inspection suggests the following memory work, ordered by evidence and
expected leverage:

1. **Measure high-water marks by workload first.** Capture the same per-client
   GPU memory metric while idle, with several mapped windows/workspaces, while
   switching workspaces, with the window switcher open, and with a fullscreen
   dmabuf-capable application. The present idle-only 62 MiB baseline cannot
   identify which retained textures are the dominant allocation.
2. **Test a low-memory wallpaper mode.** `fleetwm-wallpaper` currently paints
   an opaque XRGB8888 buffer at the output's full physical size. At 1920x1080
   one such buffer is 7.91 MiB before driver alignment/import overhead. A
   1280x720 raster would be 3.52 MiB (about 4.39 MiB less per equivalent
   backing), and 960x540 would be 1.98 MiB (about 5.93 MiB less), with an
   image-sharpness tradeoff. The current client has no fractional viewport
   scaling path for such a smaller buffer, so this needs a deliberate
   viewport/scaling implementation and a visual/memory A/B, not just a
   smaller allocation. The backing-size reduction is backend-neutral, but its
   effect on VRAM, shared memory, imports, or copies must be measured on each
   GPU class; it is not a promise of equal savings on UMA and discrete GPUs.
3. **Verify direct scanout with a real fullscreen workload.** Fleetwm already
   exposes dmabuf feedback and leaves exact, unoccluded fullscreen buffers
   eligible for wlroots' direct-scanout path. If the app submits compatible
   dmabufs, scanout can avoid a compositor composition target/copy. It is an
   existing capability to verify, not a missing optimization; overlays,
   decorations, or incompatible formats can prevent it.
4. **Only then consider releasing hidden-window textures.** Hidden workspaces
   retain mapped client buffers, so there may be resident texture memory to
   reclaim. Releasing/reimporting them could add latency, flicker, and redraw
   work when returning to a workspace. Measure retained bytes and switch cost
   before changing wlroots buffer lifetimes.
5. **Do not start by shrinking the glass caches.** Fleetwm's glass-tile,
   titlebar-glass, and caption-strip Cairo caches are byte-bounded at 3, 2,
   and 1 MiB respectively, but these are CPU-side raster caches, not a 6 MiB
   dedicated-VRAM reservation. Shrinking them may save some host memory but
   can increase redraw CPU work; it is unlikely to materially change the
   current Intel GPU allocation. `glass_backdrop_for()` can allocate one
   output-sized 32-bit backing per size (7.91 MiB at 1080p), but code search
   found no active call site, so it is not part of the measured live footprint.

An output-sized 32-bit image is 7.91 MiB at 1920x1080; Fleetkit's general
`Surface` keeps two lazy-allocated shm buffers for safe asynchronous redraws.
This client-side backing is shared system RAM; whether and how much becomes a
resident Intel GPU object depends on the wlroots/Mesa import path. Do not call
client RSS, Cairo cache bytes, or `intel_gpu_top` client memory “dedicated
VRAM.” Reducing the panel mode could reduce raster sizes but trades away
resolution and should remain an opt-in workload test, not an automatic
default.

## 2026-10-12: experiment 1, per-frame damage and commit counters (Celeron N4020 / UHD 600, nested headless 1920x1080, GLES2)

Instrumentation: `FLEETWM_GRAB_STATS=1` (src/compositor/grab_stats.hpp), harness `scripts/grab-stats-run.sh`, summary `scripts/grab-stats-summary.py`. Render/3D busy from `intel_gpu_top` per PID, 500 ms samples. Rates are per second over all rounds.

Glass on (clean run; the window was found and grabbed correctly):

| phase | pointer events/s | commits/s | damage px per commit | commit ms | Render/3D busy (compositor, median) |
|---|---|---|---|---|---|
| idle | 0 | 1.0 | 343k avg (mostly small) | 0.59 | 0.0% |
| move | 103 | 17.5 | 567k | 0.73 | 10.6% |
| resize | 122 | 24.0 | 558k | 1.22 | 17.8% (max 39%) |

Findings: no missed presentations in any phase; the 24 FPS cap holds during resize (24.0 commits/s) and the cap early-return fires about 85-105 times/s, i.e. most pointer events cost no frame. GPU busy scales with damaged pixels times commit rate (move about 9.9 Mpx/s for about 10%; resize about 13.4 Mpx/s for about 18%). A move damages about 567k px (27% of the screen) per commit, much more than the window itself, which is worth a closer look (shadow, glass and frame regions are the suspects, not verified). Resize runs the titlebar render about 20/s and the frame strip render about 61/s (CPU-side re-rendering per configure).

Caveat: the glass-off run is not usable. Its window sat 4 px away from the glass-on run, and the move and resize phases landed on the wrong targets (the "move" phase issued resize requests, the "resize" phase had no events), so there is no valid glass on/off comparison from this data. Also nested/headless (no scanout), no frame-time or input-to-present latency, 500 ms GPU sampling. No compositor change is justified yet; next would be to log damage rectangles per commit to find what makes a move damage 567k px.

### 2026-10-12 follow-up: damage rectangles, window size and glass (same laptop and setup; `GRAB_STATS_LEVEL=2`, `SHRINK_DX=400`)

Damage rectangles (RECTS lines): a move damages about one window frame per commit (about 830x655 px, plus thin slivers at the rounded corners); a resize damages the whole frame as 1-3 rectangles. Nothing outside the window is damaged except the bar clock (1920x44) now and then. So the damage is the union of the old and new window rectangles, which overlap almost completely at a few px per frame; there is no extra waste in the damage itself.

Render/3D busy, compositor only, median of 15 samples per phase, two interleaved passes (values per pass), glass on unless noted:

| window | phase | commits/s | damage px/commit | busy % |
|---|---|---|---|---|
| 800x620 content | move | 18.6, 22.8 | 570k | 10.8, 11.0 (glass off: 10.8, 10.7) |
| 800x620 content | resize | 24.0, 21.5 | 570k | 17.3, 17.5 |
| 400x620 content | move | 23.5, 23.8 | 300k | 6.2, 6.3 |
| 400x620 content | resize | 21.5, 21.9 | 310k | 10.6, 10.6 |

- Cost is proportional to damaged pixels times commit rate with no visible fixed part: about 9 ns per pixel for a move and 13-16 ns for a resize (resize also re-renders the titlebar about 20/s and the frame strip about 60/s on the CPU).
- Glass makes no measurable difference to a move (10.9 vs 10.75, n=2 per side) or a resize (17.4 vs 17.3, using the full-size run, since the glass-off shrink did not take). The glass-off 400-wide run and the glass-off 800-wide resize phase are invalid (the shrink drag missed; the resize drag found no edge) and are not used.
- intel_gpu_top's actual frequency, averaged with the idle time, is 37 MHz during a move at 10.9% busy: the GPU runs near its minimum clock (about 300-350 MHz of 1100) the whole time. The busy percentage is therefore at the lowest clock; there is clock headroom left before it would saturate.

### 2026-10-12 resize request pacing (A/B)

Change: during a resize grab the compositor sends the client a new size at most once per drag frame (1000/24 ms) and flushes the newest size when the timer fires or the grab ends (`Server::request_grab_size`, `FLEETWM_RESIZE_COALESCE=0` turns it off for comparison). Same binary, headless pixman 1920x1080, glass on, `scripts/grab-stats-run.sh --rounds 2`, two interleaved runs per arm, rates per second during the resize phase:

| arm | pointer events | resize_req | commits | titlebar_renders | strip_renders | commit_ms avg |
|---|---|---|---|---|---|---|
| off (r1/r2) | 127 / 113 | 127 / 113 | 21.5 / 19.6 | 20.2 / 18.2 | 60.6 / 54.5 | 2.81 / 2.80 |
| on (r1/r2) | 120 / 115 | 19.9 / 18.9 | 20.4 / 19.7 | 19.2 / 18.4 | 57.7 / 55.2 | 2.76 / 2.82 |

Client configure traffic drops about 6x; commits, damage and commit time do not move, and titlebar/strip renders follow the client commit rate (one per commit), so caching them per size would save nothing while every step has a new size. No GPU effect measured (nested, no scanout); the gain is fewer configure round trips and less client relayout work. Not measured: a real client under load, real DRM output.

Memory figures in the Task Manager now follow `free` (used = total - available). The memory-controller traffic row reads `uncore_imc` data_reads/data_writes and needs root or perf_event_paranoid <= 0; it was not run live (dev PC has paranoid 3), the parsers and fake-tree fallbacks are unit tested.
